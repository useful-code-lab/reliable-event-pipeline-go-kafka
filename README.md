# Надёжный пайплайн обработки событий на Go

Практический пример построения **отказоустойчивой системы обработки событий** на Go с использованием **Apache Kafka, PostgreSQL, Redis и Kubernetes**.

Проект показывает, как организовать обработку сообщений так, чтобы **дубликаты не приводили к повторной записи данных, временные ошибки обрабатывались повторно, а неисправимые сообщения не терялись**.

## Что вы получите, изучив проект

Этот репозиторий полезен разработчикам, которые хотят разобраться не только с Kafka, но и с тем, **как строить надёжные event-driven сервисы на практике**.

Из проекта можно взять готовые идеи и подходы для:

* построения Kafka Consumer на Go;
* защиты обработки от повторной доставки сообщений;
* реализации идемпотентности;
* организации Retry-механизма;
* создания Dead Letter Queue (DLQ);
* применения Transactional Outbox;
* согласованной работы Kafka и PostgreSQL;
* использования Redis для быстрой проверки дубликатов;
* корректного завершения приложения;
* запуска event-driven сервиса в Kubernetes;
* обработки временных и фатальных ошибок.

Главная ценность проекта — не отдельные технологии, а **связка механизмов, которая позволяет строить более устойчивые системы обработки событий**.

---

## Какую проблему решает проект

В распределённых системах сообщение может:

* прийти повторно;
* не обработаться из-за временной ошибки;
* содержать некорректные данные;
* быть успешно обработано, но приложение завершится до фиксации состояния;
* потеряться при неправильной организации взаимодействия между Kafka и базой данных.

Обычный Kafka Consumer не решает автоматически все эти проблемы.

В этом проекте показано, как построить дополнительный слой над обработкой сообщений:

```text
                    ┌─────────────────┐
                    │     Producer    │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │      Kafka      │
                    │  local-events   │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ Go Consumer     │
                    │ + бизнес-логика │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
              ▼              ▼              ▼
           Успех         Временная       Фатальная
                           ошибка          ошибка
              │              │              │
              ▼              ▼              ▼
        PostgreSQL        Retry Topic       DLQ
              │
              ▼
            Redis
        дедупликация
```

# Ключевые механизмы

## 1. Защита от дубликатов

Kafka может доставить одно сообщение повторно. Если обработчик каждый раз записывает его в БД, бизнес-данные могут дублироваться.

Проект использует два уровня защиты:

```text
Kafka message
      │
      ▼
Redis SETNX
      │
      ├── уже обработано → пропуск
      │
      ▼
PostgreSQL
      │
      ▼
UNIQUE(msg_key)
```

Redis позволяет быстро проверить повторную обработку, а ограничение `UNIQUE` в PostgreSQL выступает дополнительной защитой на уровне базы данных.

Пример:

```sql
INSERT INTO events (...)
ON CONFLICT (msg_key)
DO NOTHING;
```

Такой подход помогает проектировать **идемпотентные обработчики сообщений**.

---

## 2. Transactional Outbox

Одна из распространённых проблем распределённых систем:

```text
записали данные в БД
        ↓
должны отправить событие в Kafka
        ↓
приложение упало
```

В результате состояние системы может оказаться несогласованным.

Transactional Outbox позволяет сначала сохранить необходимую информацию в базе:

```text
PostgreSQL
    │
    └── kafka_outbox
             │
             ▼
        Outbox Worker
             │
             ▼
           Kafka
```

Если приложение завершится аварийно, незавершённая запись останется в Outbox и сможет быть обработана позже.

Это практический пример того, как **повысить надёжность доставки событий между компонентами системы**.

---

## 3. Retry Queue

Не каждая ошибка означает, что сообщение необходимо отклонить.

Например:

* временно недоступна база данных;
* внешний сервис вернул ошибку;
* произошёл временный сетевой сбой.

Для таких случаев используется Retry Topic:

```text
local-events
      │
      ▼
   ошибка
      │
      ▼
local-events-retry
      │
      ▼
повторная обработка
```

В проекте предусмотрено до **3 попыток повторной обработки**.

---

## 4. Dead Letter Queue

Если сообщение невозможно обработать после предусмотренных попыток, оно не должно бесконечно возвращаться в очередь.

Такие сообщения отправляются в:

```text
local-events-dlq
```

Например:

```text
Некорректный JSON
       ↓
   Consumer
       ↓
     ошибка
       ↓
      DLQ
```

Это позволяет отделить неисправимые сообщения от нормального потока обработки и сохранить их для последующего анализа.

---

## 5. Корректное завершение приложения

При остановке сервиса важно не просто завершить процесс.

Приложение последовательно:

1. прекращает чтение новых сообщений;
2. завершает текущую обработку;
3. выполняет необходимые транзакции;
4. коммитит Kafka offsets;
5. закрывает ресурсы;
6. завершает процесс.

Это демонстрирует подход к **Graceful Shutdown для Kafka Consumer**.

# Какие паттерны можно изучить

Проект объединяет несколько практических паттернов распределённых систем:

### Exactly-Once Processing

Защита от повторной обработки сообщений с использованием Redis и ограничения уникальности в PostgreSQL.

### Transactional Outbox

Сохранение событий перед их публикацией, чтобы уменьшить риск потери данных при сбоях.

### Retry Queue

Повторная обработка сообщений после временных ошибок.

### Dead Letter Queue

Изоляция сообщений, которые невозможно обработать автоматически.

### Graceful Shutdown

Корректное завершение Kafka Consumer без резкого прекращения текущей обработки.

# Запуск в Minikube

## 1. Запустить Minikube

```bash
minikube start --cpus=3 --memory=4096
```

## 2. Подключить Docker к окружению Minikube

```bash
eval $(minikube docker-env)
```

## 3. Собрать Docker-образ

```bash
docker build -t kafka-pipeline-go:local .
```

## 4. Развернуть инфраструктуру

```bash
kubectl apply -f k8s-kafka.yaml
```

## 5. Создать Kafka Topics

Основной topic:

```bash
kubectl exec -it deployment/kafka-deployment \
-- kafka-topics.sh \
--create \
--topic local-events \
--bootstrap-server localhost:9092 \
--partitions 3 \
--replication-factor 1
```

DLQ:

```bash
kubectl exec -it deployment/kafka-deployment \
-- kafka-topics.sh \
--create \
--topic local-events-dlq \
--bootstrap-server localhost:9092 \
--partitions 1 \
--replication-factor 1
```

## 6. Перезапустить приложение

```bash
kubectl rollout restart deployment/go-kafka-app
```
